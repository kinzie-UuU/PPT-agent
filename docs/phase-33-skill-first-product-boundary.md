# Phase 33: Skill-First Product Boundary

## Conclusion

The product must treat `codex-ppt` and `image-to-editable-ppt` as the core engines.
Local code should orchestrate, persist state, expose UI, manage provider/runtime
configuration, and preserve evidence. It should not become a third PPT conversion
engine.

The 15-page `个性创意定制案例-1.pptx` run is a regression fixture only. It must not
define the product architecture, default quality bar, or product UX. Future inputs
may be PPT/PDF/images or a plain brief; the default flow must still follow the two
Skill contracts below.

## Core Skill Contracts

### codex-ppt

- Owns visual reinterpretation and unified image-based deck generation.
- Requires outline/style/backend/sample approval gates.
- Final slide images must be generated by the selected image backend and recorded.
- Local drawing, manual overlays, HTML screenshots, or python-pptx layout generation
  are not valid replacements for the skill's image generation path.

### image-to-editable-ppt

- Owns image/PDF/image-based PPT to object-level editable PPT reconstruction.
- Must use the `editppt` state machine:
  `prepare -> dispatch -> record -> finalize`.
- Multi-page page artifacts must be produced by the page worker that owns the
  page directory. Single-page inputs use v0.3 local page-reconstructor mode after
  `editppt run dispatch --local` claims the page.
- Foreground visual assets must go through serial `editppt image generate/edit`
  and related import/process-sheet commands.

## Local Product Responsibilities

Keep:

- Upload/import and file management.
- Job state, queue state, logs, artifacts, and resumability.
- API/provider/runtime configuration.
- UI for progress, page review, prompt visibility, worker dispatch, retry, and export.
- `editppt` command orchestration and state inspection.
- Guardrails that keep outdated local rebuild/generation paths out of the default
  product flow.

Keep only as worker-side helper:

- `page-worker-pipeline.mjs`, only as `lab:page-pipeline`, and only inside a
  real worker session after the worker has authored the page decisions.
- `visual-asset-helper.mjs`, only as `lab:visual-assets`, and only when it wraps
  `editppt image ...` and records image imports/process-sheet output.
- `page-rebuild-assembler.mjs`, only as `lab:assemble-page`, and only inside the
  worker-owned page directory.

Experimental only:

- `local-page-worker.mjs`
- `model-page-spec-worker.mjs`
- `model-page-worker-pipeline.mjs`
- Any automatic model-authored `page-rebuild-spec.json` flow.
- Local crop/inpaint fallback in `visual-asset-helper.mjs`.
- Any old local one-click PPT generation path that does not go through codex-ppt
  approvals and image-to-editable-ppt reconstruction.

These experimental paths may be useful for regression, debugging, or fallback
research. They must not be presented as the normal product path.

## Cleanup Decisions Applied

- Local OpenCV crop/inpaint asset fallback is disabled by default.
- It now requires `--allow-local-fallback` or
  `PPT_TOOL_ALLOW_LOCAL_ASSET_FALLBACK=true`.
- The frontend labels the model worker runner as experimental.
- Experimental model-worker commands are no longer shown in the default worker
  action row. They live under a Lab section so the normal product path remains
  skill-first.
- The text-only local worker command also lives under Lab. It remains useful for
  smoke tests, but it is not the normal product reconstruction path.
- Added a skill compliance API and frontend panel. It summarizes codex-ppt visual
  deck progress, image backend configuration, editppt prepare/prompt/record/finalize
  state, and explicit experimental fallback evidence.
- The default worker console now prioritizes the official page-worker handoff:
  copy the generated prompt, spawn a real worker, then dispatch/record through
  editppt. Worker-side helper commands live under Advanced, while local/model
  recovery runners remain under Lab.
- Added a final delivery gate. A generated PPTX is labeled as product-ready only
  when validation, editability, full-slide raster checks, default-path evidence,
  and manual review status all pass. Otherwise the UI labels it as draft or
  blocked and shows the reasons.
- Added manual review recording. The workflow review panel can mark the current
  final PPTX as reviewed or reset that review; the gate only counts the review
  when it matches the current final artifact. Review evidence does not waive
  full-slide raster, experiment-path, validation, or editability failures.
- Expanded skill compliance diagnostics. The API/UI now reports codex-ppt
  approval-gate evidence, fixed visual image backend evidence, `editppt doctor`
  status, and the `editppt image generate/edit` backend contract reported by
  prepare.
- Added first-class codex-ppt approval recording. The workflow UI can now record
  or reset outline, style, backend, sample, and full-deck approvals, and the
  backend stores those records in `artifacts.codexPptApprovals`.
- The default workflow create action no longer dry-runs all the way to page
  worker prompts. It creates the workflow, renders source pages, and stops for
  explicit codex-ppt approvals before visual generation.
- Added backend approval gates for visual generation. `/visual/sample` now
  requires outline, style, and backend approvals; `/visual/generate` additionally
  requires sample approval and full-deck authorization. Missing approvals return
  `CODEX_PPT_APPROVAL_REQUIRED` without marking the visual stage as failed.
- Added page-worker evidence scanning. Compliance and delivery status now inspect
  each `editppt` page directory for dispatch/result records, required page
  artifacts, top-level `validation.passed`, `page_result.json` shape, manifest
  contract basics, and recorded output hash matches.
- Added finalize evidence scanning. Compliance and delivery status now verify
  the final PPTX against `editppt run finalize` evidence: run summary,
  workspace/run validation files, final output copy size/hash, page counts, and
  empty deck-level validation failure arrays.
- Added codex-ppt evidence to the final delivery gate. A final PPTX now remains
  blocked unless all outline/style/backend/sample/full-deck approvals are
  recorded and the fixed visual image backend evidence is present, consistent,
  and not passthrough/dry-run.
- Renamed experimental local/model rebuild script entrypoints from `worker:*` to
  `lab:*`, then moved page artifact helper commands (`page-pipeline`,
  `visual-assets`, and `assemble-page`) into `lab:*` as well. The default
  `worker:*` namespace now stays focused on orchestration only: claim/dispatch,
  batch execution, and worker brief generation.
- Expanded `audit:entrypoints` to report `worker:*`, `lab:*`, and any
  local/model experimental command accidentally exposed as a default worker
  script.
- Added `regression:skill-first`. It verifies the default upload ->
  workflow-create -> source-render path stops before visual generation, verifies
  codex-ppt approval-gate blocking, confirms blocked approval attempts do not
  mark workflow stages as failed, and checks that experimental local/model
  commands remain under `lab:*`.
- Updated `regression:real-ppt` to follow the approval-gated product boundary:
  it now proves `visual/generate` is blocked before approvals, then records
  regression-only approvals before dry-run passthrough.
- Removed the broken hard-coded real PPT regression default path. Real deck
  acceptance now requires `--source`, `PPT_TOOL_REAL_PPT_SOURCE`, or an explicit
  `--latest-download-pptx` opt-in.
- Tightened v1 readiness evidence so provider runtime checks also report whether
  the approved codex-ppt backend model/base URL still matches the current
  runtime configuration.
- Changed editable worker prompt generation to default to every
  `dispatchable_pages` entry instead of only the current concurrency window's
  `suggested_pages`. This keeps v1 acceptance jobs from requiring a manual
  second prompt-build step for later pages.
- Advanced the 15-page real PPT acceptance fixture
  `workflow_20260623-035703Z_88b7a7` through editppt prepare and full-page
  worker prompt sync: 15 text-hint pages, 305 text hint lines, and 15/15 editable
  worker tasks ready.
- Added visual image provenance manifests. Generated visual pages now keep
  provider/model/base URL, dry-run state, prompt, size, dimensions, and sha256
  evidence after folder discovery and image-deck assembly. Dry-run passthrough
  remains visibly marked as passthrough and cannot be mistaken for a fixed
  codex-ppt backend result.
- Added a skill-first runbook to compliance diagnostics. The UI now shows the
  current required phase, allowed next actions, blocked reasons, and every major
  codex-ppt/editppt step from source rendering through final review.
- Tightened codex-ppt sample evidence. Sample approval without a visual sample
  artifact is now a compliance failure, the runbook blocks full-deck generation
  until sample artifact plus approval both exist, and final delivery reports
  missing sample evidence as a codex-ppt blocker.
- Moved codex-ppt approval preconditions into the backend approval API. Backend
  approval now requires a configured non-passthrough image provider unless the
  caller explicitly marks a regression/non-product path, sample approval requires
  prior outline/style/backend approvals plus a visual sample artifact, and
  full-deck authorization requires the approved sample evidence.
- Blocked non-product visual generation by default. `visual/sample` and
  `visual/generate` now require a configured external image backend and reject
  `dryRun`/`passthrough` unless the caller explicitly marks a regression or
  non-product visual path. Rejected non-product visual requests return a
  structured `CODEX_PPT_*` 409 response and do not mark the workflow stage
  failed.
- Added `product:visual-readiness`. Its default mode performs a no-cost
  product-path readiness check: server health, image provider configuration,
  source rendering, codex-ppt outline/style/backend approvals, and runbook
  transition to the sample stage. It accepts `--source <file>` for real
  PPT/PDF/image inputs instead of only using a synthetic source. Passing
  `--generate-sample` intentionally spends one configured external image API
  call and verifies the resulting sample is not passthrough/dry-run and has
  provenance. Passing `--generate-sample --generate-deck --max-pages N`
  additionally authorizes fullDeck, generates N product visual images, verifies
  per-image provenance, and assembles the image-based PPTX before handing off
  to editppt prepare.
- Moved the frontend primary generate action onto the Skill-first workflow
  creator. The visible primary action now creates a workflow, renders the
  uploaded source, and stops for codex-ppt approvals instead of calling the old
  local `/api/jobs/generate` or `/api/jobs/optimize` one-click path. The old
  path remains available only under a Lab disclosure for comparison/recovery.
- Extended `regression:skill-first` to assert this frontend boundary: the
  primary action must call `startSkillFirstWorkflow`, while the legacy one-click
  generator must stay Lab-labeled.
- Added a brief-only Skill-first input path. When no PPT/PDF/image is uploaded,
  the frontend now writes the current project brief, style preference, material
  signals, and confirmed outline into a workflow `source.md`; `source/render`
  records it as a `brief-source` page and moves the run into the same codex-ppt
  approval-gated path. This does not create slide images or a final deck by
  itself.
- Added `product:visual-readiness -- --brief "..."` for no-cost readiness checks
  without using the 15-page regression fixture or a synthetic PNG source.
- Added target slide-count evidence for brief readiness checks. A brief may
  render as one source page while still producing a multi-slide codex-ppt
  outline through `--slides`, `--slide-count`, or an inferred "N-page/slides"
  phrase.
- Added first-class codex-ppt outline artifacts. Skill-first workflow creation
  now records `codex-ppt/outline.json` and `codex-ppt/outline.md`; the outline
  approval gate refuses approval until that evidence exists. Compliance,
  artifact links, readiness checks, regression scripts, and final delivery gates
  all expose or enforce this outline evidence.
- Added first-class codex-ppt style and backend decision artifacts. The workflow
  now records `codex-ppt/style.json`, `codex-ppt/style.md`,
  `codex-ppt/backend.json`, and `codex-ppt/backend.md`; the style and backend
  approval gates refuse approval until their decision evidence exists.
  Compliance, artifact links, readiness checks, regression scripts, and final
  delivery gates all expose or enforce these decision artifacts.
- Added codex-ppt full-deck run-state artifacts after sample/full-deck approval.
  `visual/generate` now records `codex-ppt/deck_spec.json`, `speech.md`,
  per-slide `prompts/slide_XX.json`, `slide_jobs.json`, and
  `slide_run_state.json`. Each generated visual page updates dispatch/result
  state, and regression asserts `deck_spec`, slide jobs, prompt count,
  dispatched count, recorded count, and visual provenance.
- Added a first codex-ppt slide-worker task queue. The server exposes sync/list,
  claim, heartbeat, complete, and reset APIs for slide image workers; the CLI
  entrypoint is `npm.cmd run worker:codex-slide -- ...`. This is the product
  direction for replacing server-local visual generation with explicit worker
  claim/return evidence.
- Added a no-shell codex-ppt slide batch runner. The API/frontend can run ready
  slide tasks through the configured external image provider after full approval
  and explicit spend confirmation, while regression can opt into non-product
  placeholder images without consuming provider credits.
- The codex-ppt slide batch runner can now assemble the image-based PPTX after
  all slide tasks are recorded, preserving the `codex-ppt -> image deck ->
  image-to-editable-ppt` handoff without requiring a shell command.
- The codex-ppt slide batch runner can now optionally call `editppt prepare`
  immediately after image-deck assembly. This keeps the normal product path on
  `codex-ppt -> image deck -> image-to-editable-ppt/editppt prepare` without
  requiring the user to run a separate shell command.
- The same batch path can now build editppt page-worker prompts and sync them
  into editable worker tasks after prepare. That gives the UI a ready queue for
  dispatch/record/retry instead of leaving the user at a manual CLI handoff.
- Background editable worker batch runs now persist their parsed completion
  summary: requested pages, succeeded/failed counts, per-page results, and the
  resulting task summary. The UI polls running batches and displays this summary
  beside the log links so page reconstruction progress is visible without shell
  access.
- When a background editable worker batch completes successfully and editppt
  reports every page task recorded, the product runner can automatically call
  `editppt run finalize` through `finalizeWorkflowEditableRun`. The final PPTX
  and validation still come from the image-to-editable-ppt state machine; the
  product wrapper only removes the extra manual finalize click.
- Background editable model worker batches now require the same explicit spend
  confirmation pattern as codex-ppt slide image batches. The frontend shows a
  checkbox plus a final confirmation dialog with ready page count and image
  model; the backend rejects `mode=model` worker batches unless
  `confirmExternalImageSpend=true` is present. The frontend also passes
  `autoFinalize` through the worker batch API instead of only setting it in
  local state.
- Added a no-cost editable worker batch preflight API. Before starting the
  model page-worker batch, the frontend can show selected task count, provider
  model, editable pages remaining, required confirmations, warnings, and hard
  blockers. The preflight distinguishes `ready` state from `startReady`, so the
  UI can tell the difference between missing user confirmation and missing
  workflow artifacts/provider configuration. Confirmation checkbox changes
  refresh preflight immediately, so the page shows when the batch is actually
  start-ready before the user presses the start button.
- Editable worker batch start is single-flight per workflow. If a prior
  background batch is still running, the backend rejects a second start request
  and preflight reports the active runner with log links. This protects page
  records from duplicate workers and avoids accidental duplicate external image
  API spend.
- Editable worker batch start now reuses the same preflight gates as the UI.
  The backend rejects non-start-ready batches before creating runner logs or
  spawning `page-worker-batch.mjs`, and it pins the actual `--pages` list to the
  preflight-selected ready/failed tasks. This keeps direct API calls aligned with
  the visible no-cost readiness check instead of relying on frontend-only guard
  logic.
- Cleaned the shared delivery-status copy and added a structured `nextStep`.
  The delivery panel now tells the operator whether the workflow is waiting on
  source rendering, image deck generation, editppt prepare, page workers,
  finalize, validation review, or final download. This keeps the product console
  from showing mojibake status text and reduces black-box waiting near final
  delivery.
- The product v1 acceptance API and panel now surface the same delivery
  `nextStep` plus editable worker counts. The acceptance checklist no longer
  only says that final PPTX evidence is missing; it also shows whether the next
  concrete action is page-worker dispatch, finalize, validation review, or final
  download.
- The v1 acceptance panel now exposes an `Open step panel` action for the
  current delivery step. Page-worker steps jump to the editable worker console,
  image-deck steps jump to the codex-ppt slide worker panel, and validation or
  final-review steps jump to the delivery gate. This turns v1 readiness from a
  passive checklist into an operator handoff without starting any external
  image API work automatically.
- v1 readiness now includes a compact no-cost editable worker batch preflight.
  The acceptance panel shows selected page count, provider model, external API
  spend confirmation, offline text-hint confirmation, and the first blocking or
  warning messages. This makes the final handoff explicit before any real
  `image-to-editable-ppt` worker batch can spend external image API credits.
- v1 readiness now groups preflight actions separately from acceptance evidence.
  Confirmation items such as external image API usage and offline text hints are
  shown first under `To start batch`, while missing final PPTX/validation
  evidence remains in the acceptance checklist. This keeps operator-resolvable
  setup work distinct from work that requires a real worker run.
- v1 readiness now groups provider runtime actions separately from worker
  preflight and acceptance evidence. If the approved codex-ppt backend evidence
  is dry-run/regression/passthrough or no longer matches the configured image
  runtime, the API and UI show a `Runtime evidence` action that points the
  operator back to codex-ppt visual generation instead of pretending the old
  evidence proves product readiness.
- Added a no-cost codex-ppt slide batch preflight. The API reports approval
  gates, synced slide-task counts, selected runnable pages, configured image
  provider, expected image calls, and the external spend confirmation state
  before any full-deck visual generation starts. The v1 acceptance panel now
  shows this as `codex-ppt visual preflight`, so visual generation readiness is
  visible separately from editable page-worker readiness.
- Added a guarded reset path for non-product codex-ppt slide evidence. The API
  can preview recorded slide tasks that look like regression/dry-run/passthrough
  results, and only resets them to `ready` when `confirmNonProductReset=true` is
  provided. The frontend exposes this as `Reset dry-run results`; it does not
  delete existing files or reset recorded product-looking slide evidence.
- After a confirmed non-product slide reset, the API now returns a
  `postResetPreflight` bundle. The frontend reports how many slide tasks are
  ready for the product runtime rerun and reminds the operator to confirm
  external image API usage before starting the provider batch.
- The codex-ppt slide task panel now shows the slide batch preflight directly:
  selected slide count, ready count, provider model, expected image calls,
  approval status, and an explicit external image API confirmation checkbox.
  `Run provider batch` stays disabled until this preflight is start-ready.
- The codex-ppt slide batch preflight now also checks backend approval evidence
  against the current image runtime. Product visual generation is blocked when
  the approved backend still looks like regression/dry-run/passthrough evidence
  or no longer matches the configured `gpt-image-2` runtime. The UI shows this
  as `Backend approval` so operators know to re-approve/re-run codex-ppt visuals
  before spending image API credits.
- Added a no-cost frontend `Refresh backend approval` recovery action. When an
  approved backend is stale or non-product, the operator can refresh the backend
  decision from the current provider configuration and re-approve the backend
  gate. The action intentionally resets `sample` and `fullDeck` approvals too,
  because a new backend requires a fresh visual sample review before full-deck
  generation can be authorized again.
- The backend refresh is now exposed as one no-cost API action:
  `POST /api/workflow-jobs/:id/codex-ppt/backend/refresh-approval`. The frontend
  calls this single route instead of manually chaining reset/record/approve calls,
  so backend/sample/fullDeck invalidation and the refreshed backend approval stay
  consistent even if the UI is interrupted.
- The refresh route now performs its own runtime/approval comparison before
  mutating workflow state. If the approved backend already matches the current
  runtime and is not dry-run/passthrough, the route returns the current job
  without resetting `sample` or `fullDeck` unless `forceRefresh=true` is sent.
- The v1 acceptance provider action now points operators to the backend refresh
  approval panel when runtime evidence is stale. It no longer sends users straight
  to slide batch generation while the backend approval still needs to be refreshed.
- The v1 acceptance `deliveryNextStep` is now the effective product next step.
  When provider runtime evidence is stale or dry-run, it is overridden to
  `refresh-backend-approval`; the raw delivery step remains available as
  `delivery.rawNextStep` for diagnostics.
- The effective v1 next step also prioritizes incomplete codex-ppt visual
  evidence over editable page workers. If sample/full-deck approval is missing
  or recorded slide images are still dry-run/passthrough, the UI stays on the
  codex-ppt visual panel instead of starting `image-to-editable-ppt` too early.
- Sample and full-deck approvals now reject dry-run/passthrough visual sample
  evidence on the product path. Regression callers can still opt in explicitly,
  but a refreshed backend cannot accidentally approve the old passthrough sample.
- Updated the real PPT regression so the 15-page fixture exercises the
  codex-ppt slide-worker queue in regression-only passthrough mode. That confirms
  the queue contract without treating the fixture output as product quality.
- Updated the local `image-to-editable-ppt` skill/runtime to v0.3.0. The product
  now treats `rebuild_page_locally` as the expected single-page editppt stage,
  supports `editppt run dispatch --local`, routes foreground image work through
  serial `editppt image generate/edit`, and protects dispatched page resets with
  matching `agent-id` plus `--confirm-lost`.
- Added a guarded single-page local rebuild API for v0.3.0. It claims the page
  with `dispatch --local`, runs the existing text-dominant local reconstructor,
  records through `editppt run record`, and can finalize. Because this runner
  does not perform full foreground asset separation, callers must explicitly set
  `allowTextDominantLocal=true` or `regression=true`; it is not a replacement for
  the future full visual local reconstructor.
- Moved the old workflow `ocr/run` action out of the default frontend action
  row and into a Lab-only diagnostics panel. The product path now presents
  `image-to-editable-ppt` / `editppt` text hints as the normal text extraction
  evidence, while legacy source OCR remains available only for comparison and
  regression troubleshooting.

## Acceptance Direction

A future product-ready run should be considered successful only when:

- `codex-ppt` completes its approval-gated visual deck generation path.
- `image-to-editable-ppt` completes `editppt` prepare/dispatch/record/finalize.
- No experimental local fallback is used unless explicitly enabled and reported.
- The UI exposes page-level review and rerun controls before final delivery.
